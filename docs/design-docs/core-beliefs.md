# InferBench 核心工程原则

本文将 OpenAI 的 [Harness engineering](https://openai.com/zh-Hans-CN/index/harness-engineering/) 范式适配到 InferBench。目标不是追求“AI 生成代码”的数量，而是让智能体能在清晰边界和快速反馈中可靠完成真实工程任务。

## 1. 人类掌舵，智能体执行

管理员决定产品优先级、验收标准、PR 是否合并以及发布版本。智能体负责读取仓库记录、设计改动、实现、验证、提交 PR、响应反馈和检查 CI。

## 2. 仓库是记录系统

对未来智能体有用的事实不能只存在于对话、即时消息或个人记忆中。产品契约、架构决策、执行计划、失败原因和验证证据必须进入版本控制。

`AGENTS.md` 是短地图；详细信息分布在结构化文档中，通过渐进式披露减少无关上下文。

## 3. 优先建设反馈回路

当智能体反复失败时，优先补齐缺失的工具、可观察性、文档或机械约束，而不是重复同一个模糊提示。

本仓库的标准反馈入口是：

```bash
./scripts/verify.sh
```

它应给出可定位、可修复的错误，并在本地和 CI 中保持一致。

## 4. 强制边界，不微观管理实现

中央规则关注安全、正确性和结构：数据在边界解析、API Key 不落盘、依赖方向固定、历史样本可复算、发布 Tag 受审批。边界之内允许智能体选择最清晰且可维护的实现。

## 5. 可读性是产品能力

API、日志、状态、错误和 UI 必须便于人类与智能体检查。测试应能复现缺陷并验证行为；错误消息应说明违反了什么不变量以及如何修复。

## 6. 计划和证据是一等工件

复杂任务使用版本化执行计划，记录目标、范围、决策、进度和验收证据。PR 不是只有代码差异，还应包含可复核的意图和验证结果。

## 7. 持续清理熵

智能体会复制仓库中的好坏模式。通过每周 CI、质量记录和小型重构持续偿还技术债务，避免定期进行高风险的大扫除。

## 8. 人类判断保留在明确的门上

InferBench 不采用自动合并和自动决定版本：

1. 管理员明确确认并合并 PR。
2. 合并后，管理员再次明确确认准确的发布 Tag。

其余可机械验证的环节尽量自动化，避免把人类注意力消耗在重复检查上。
